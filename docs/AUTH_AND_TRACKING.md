# Jol: телефонный вход, приватные данные и передача позиции

Статус: реализация и проверки на эмуляторах. Настоящие SMS, production Firebase и передача между физическими iPhone пока не проверены. Локальная CLI авторизована; подключение облачного проекта выполняется отдельно.

## Как устроен вход

1. При регистрации Firebase Phone Auth подтверждает номер SMS-кодом. Эта сессия имеет provider `phone`, поэтому не может читать профиль, заказы, поездки, фото или GPS.
2. `registerPhone` проверяет свежесть подтверждения (5 минут), соответствие номера Firebase Auth и UID, валидирует профиль, создаёт серверный verifier и уникальный индекс номера транзакционно.
3. Пароль хранится только как salted scrypt verifier: N=131072, r=8, p=1, 16 случайных байт соли, 64 байта результата. Сравнение выполняется через timingSafeEqual. Ввод: 6–128 Unicode code points, до 512 UTF-8 байт; пробелы сохраняются, пароль не обрезается. Зависимости для собственной криптографии не добавлены.
4. Обычный вход проверяет телефон и пароль, создаёт `authSessions/{uuid}` и выдаёт Firebase custom token с `jolSession` и `jolVersion`. Business API и rules требуют provider `custom`, неотозванную сессию, совпадение UID и текущей версии.
5. Сессия действует до 30 дней. Firebase SDK управляет токенами; пароль в файлы/UserDefaults не записывается. При выходе приложение отзывает свою серверную сессию. Если сеть недоступна, очищает локальный вход; точка GPS скрывается через 2 минуты без обновлений.
6. Восстановление требует нового свежего SMS-proof, сохраняет UID и меняет случайную версию. Старые сессии сразу перестают проходить rules/Functions, даже если их Firebase ID token ещё не истёк. Повтор того же proof отклоняется. После reset выполняется вход новым паролем.
7. Прежний email-аккаунт переносится через подтверждение email/password и привязку/повторную проверку phone credential на том же UID. Номер из неподтверждённого поля старого профиля не используется для слияния. Не следует менять номера через Firebase Console без отдельной миграции индекса.

App Check обязателен для всех production callable endpoints. Проверка пароля ограничена 8 попытками на идентификатор и 30 на IP за 15 минут. Scrypt Functions: 512 MiB, concurrency 2, maxInstances 5. Логи не содержат паролей, кодов, токенов и координат. Все business-транзакции повторно проверяют сессию внутри транзакции, чтобы reset/logout не обошёл авторизацию через гонку.

Основания: [Firebase Phone Auth](https://firebase.google.com/docs/auth/ios/phone-auth), [custom tokens](https://firebase.google.com/docs/auth/admin/create-custom-tokens), [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Перед production выполнить проверку нагрузки scrypt в выбранном регионе и настроить наблюдение за отказами/бюджетами.

## Фото и кэш

Firestore в приложении использует память вместо дискового кэша для реальных аккаунтов. Демо по-прежнему хранится отдельным LocalRepository.

Фото передаются через callable Functions с полной проверкой сессии и ACL заказа. Причина: Storage Rules позволяют только два Firestore lookup, а проверка сессии, отзыва, версии и участия в заказе требует больше. Прямой клиентский доступ к Storage закрыт. [Ограничения Security Rules](https://firebase.google.com/docs/rules/rules-behavior)

Загрузка принимает JPEG до 5 МБ и использует уникальное неизменяемое имя объекта. Повтор после неизвестного результата публикации возвращает тот же заказ/фото. Неопубликованные фото старше 48 часов убирает плановая функция; связанное фото остаётся до удаления аккаунта/заказа. Длительность при ошибках Cloud Scheduler нужно контролировать в мониторинге.

## Несколько посылок

Одна поездка принимает до заданного перевозчиком лимита (1–10) и общей массы. Для первой версии запас рассчитывается консервативно: суммарный вес всех принятых посылок, включая уже доставленные; отменённая освобождает запас. Это исключает перегруз, не требует вычислять пиковую загрузку на каждом участке и не продаёт одно место повторно.

Порядок: точка отправления → получение/передача первой посылки → получение/передача второй → … → конечная точка. Оптимизатор перестановок не реализуется. Каждая автомобильная часть берётся из MKDirections. До согласия обеих сторон новые адреса доступны только как приблизительные районы; detour явно предварительный. После принятия перевозчик видит точные остановки. Его маршрут и список чужих заказов не выдаются другим отправителям.

В текущем MVP предел объезда — пожелание перевозчика, а не подтверждённый сервером дорожный расчёт. UI показывает превышение и требует явного подтверждения при принятии. Если Apple не рассчитывает дорогу, результат — «неизвестно», а решение принимается после обсуждения с отправителем. Цена не списывается автоматически.

## Передача позиции

- Перевозчик самостоятельно включает передачу в заказах `enRoute` / `pickedUp`. Core Location запрашивается по нажатию. Background location включён только при активной передаче; системный индикатор виден. Отдельное Always-разрешение не запрашивается автоматически.
- Для каждой активной доставки сервер создаёт lease, привязанный к UID, заказу и конкретной auth-сессии. Несколько посылок могут иметь отдельные активные leases одного перевозчика.
- Клиент публикует свежую позицию при перемещении примерно на 50 м, не чаще раза в 15 секунд; без движения целевой интервал 60 секунд при наличии свежего GPS. Сервер дополнительно ограничивает обновления до одного в 10 секунд на заказ.
- Порядок проверяется по lease, монотонному sequence и времени измерения; старые, неточные (>1000 м) и просроченные (>60 с) точки отклоняются. Повтор sequence идемпотентен. Координаты не логируются и не складываются в историю.
- Через 60 с без обновления UI показывает устаревшую позицию. Через 120 с read запрещён rules и точка скрывается таймером UI.
- Доставка/отмена закрывают lease и удаляют точку в одной транзакции. Ручная остановка, logout и отзыв разрешения прекращают Core Location. Logout/reset также закрывает чтение через auth-сессию/версию издателя.
- Последняя точка находится только в `deliveries/{id}/private/liveLocation`. Она получает срок хранения 23 ч; hourly cleanup удаляет просроченные точки, TTL служит дополнительной уборкой. Удаление TTL асинхронно и не является механизмом доступа. Политики TTL и Scheduler нужно действительно развернуть перед выпуском.
- Завершённая iOS-программа, выключенный телефон и отсутствие связи не гарантируют фоновую доставку обновлений. Расход батареи, блокировка экрана и длительное движение требуют отдельного испытания на двух реальных устройствах.

## Что требуется для настоящего подключения

1. Создать Firebase project; включить Authentication → Phone и SMS region policy для Казахстана. Включить Blaze с бюджетными уведомлениями (они не являются жёстким пределом расходов).
2. Добавить iOS app с Bundle ID основной схемы. Скачать `GoogleService-Info.plist` в `App/Resources/`, не добавляя его в Git. Запустить генератор проекта.
3. В игнорируемом `App/Resources/LocalSigning.xcconfig` установить `JOL_AUTH_CALLBACK_SCHEME` равным Encoded App ID из Firebase. Проверить redirect/reCAPTCHA. Подключить APNs key и подпись с поддержкой нужных capabilities; Personal Team Demo остаётся изолированной.
4. Настроить App Check App Attest; debug tokens разрешать только для тестовой среды. Не отключать production enforcement.
5. Создать Firestore/Storage, проверить регион, затем деплоить Functions, rules, indexes/TTL и Scheduler. Проверить IAM custom-token signing для service account (`iam.serviceAccounts.signBlob` по наименьшим нужным правам).
6. Проверить на реальных номерах регистрацию, обычный вход, reset, silent APNs и reCAPTCHA. После этого — два iPhone, предложения, принятие, GPS foreground/background/locked/offline и остановку.

Ни один из этих облачных шагов не считается выполненным по факту git push. Пока Google/Firebase не подключены, используйте JolParcelDemo для карт и локального сценария, а Firebase Emulator Suite — для серверных правил и транзакций.
